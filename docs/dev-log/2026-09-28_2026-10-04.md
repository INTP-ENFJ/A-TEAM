## 2026-09-30 — 새 프로젝트 생성 RPC 파라미터 불일치 오류 해결

### 추가한 기능
- 없음 (기존 기능 연결 정상화 작업)

### 변경한 기능
- 프론트엔드 프로젝트 생성 모달의 RPC 함수 호출 인자 구조 정렬

### 발생한 오류
- **오류 메시지**: `Could not find the function public.create_project_with_initial_article(...) in the schema cache`
- **개발자용 설명**: 프론트엔드 코드에서 Supabase RPC `create_project_with_initial_article`를 호출할 때 DB 스키마에 정의되지 않은 `desk`, `reporterName` 파라미터를 함께 전달하여 Postgres 함수 시그니처 매칭에 실패하고 PostgREST 스키마 캐시 에러가 반환됨.
- **일반인 설명**: 새 프로젝트를 만들 때 화면에서 서버로 보내는 정보의 이름과 서버가 받도록 정해둔 정보의 이름이 서로 달라 프로젝트 생성이 실패함. 화면과 서버 사이의 정보 전달 규격이 일치하지 않아 발생한 오류임.
- **발생 시점 (파이프라인)**:
  - 전체 파이프라인: `[모달 입력] → [1. 프로젝트 생성 RPC 호출] (실패) → [2. 초기 기사 생성] → [3. 프로젝트 화면 이동]`
  - 실패 지점: 1단계 프로젝트 생성 RPC 호출 단계

### 원인
서버 DB에 정의된 RPC 함수는 `project_title`, `article_title`, `category`, `coverage_type`, `deadline` 등을 요구했으나, 프론트엔드에서 과거 레거시 구조인 `desk`, `reporterName`을 그대로 전송하고 있었음.

### 해결 방법
1. 백엔드 DB 함수나 마이그레이션을 임의로 수정하지 않음.
2. 프론트엔드 호출부에서 불필요한 `desk`, `reporterName` 전달을 제거.
3. 서버가 요구하는 `category`, `coverageType`, `deadline` 규격으로 페이로드를 매핑하고, 작성자 및 소유자는 인증 세션(`auth.uid()`)을 기준으로 자동 처리되도록 유지.

### 검증 결과
- **수정 파일**: 프론트엔드 프로젝트 생성 컴포넌트 1개
- **DB / RLS / Edge Function 변경 여부**: 변경 없음
- **TypeScript 컴파일 및 프로덕션 빌드**: 통과 (`tsc --noEmit`, `vite build`)
- **실제 브라우저 E2E 검증**:
  - 새 프로젝트 생성 성공
  - 초기 기사 및 첫 문단 생성 성공
  - 프로젝트 소유자와 기사 작성자 정상 지정
  - 기사 상태 `draft` 정상 진입 확인

### 상태
완료

### PPT용 한 줄 요약

## 2026-09-30 — 미디어 업로드 crypto.randomUUID 미지원 호환성 해결

### 추가한 기능
- Web Crypto 표준 기반 안전한 UUID fallback 생성 유틸리티

### 변경한 기능
- 미디어 파일 업로드 경로 생성 로직 개선 (`src/services/mediaService.ts`)

### 발생한 오류
- **오류 메시지**: `crypto.randomUUID is not a function`
- **개발자용 설명**: 미디어 파일을 Supabase Storage에 업로드하기 전 고유 저장 경로(UUID)를 생성하는 과정에서 `crypto.randomUUID()`를 직접 호출했으나, 현재 브라우저 실행 환경(구형 엔진 또는 보안 컨텍스트 미충족)에서 해당 메서드를 지원하지 않아 `TypeError`가 발생하며 업로드가 조기 차단됨.
- **일반인 설명**: 사진을 저장하기 전에 사진마다 겹치지 않는 고유한 번호를 만들어야 하는데, 현재 브라우저 환경에서 최신 고유 번호 생성 기능을 지원하지 않아 사진이 서버에 올라가기 전에 작업이 멈춤.
- **발생 시점 (파이프라인)**:
  - 전체 파이프라인: `[파일 선택] → [파일 검증] → [고유 UUID 생성] (실패) → [Storage 업로드] → [DB 메타데이터 저장] → [Gemini AI 분석]`
  - 실패 지점: 3단계 미디어 고유 UUID 생성 단계

### 원인
`crypto.randomUUID`는 최신 웹 표준이나 특정 브라우저 또는 컨텍스트 환경에 따라 미지원될 수 있음에도 대체 수단 없이 단독 호출됨.

### 해결 방법
1. 보안 수준이 낮은 `Math.random()`을 사용하는 임시방편을 철저히 배제.
2. 환경에 `crypto.randomUUID`가 존재하면 최우선으로 사용.
3. 미지원 시 `crypto.getRandomValues()`를 활용하여 RFC4122 v4 표준을 준수하는 암호학적으로 안전한 UUID 생성 fallback 로직을 구현.
4. 암호화 난수 생성기 자체를 전혀 지원하지 않는 비정상 환경에서는 조용히 취약한 난수를 만들지 않고 명시적 에러를 발생시키도록 방어.

### 검증 결과
- **수정 파일**: `src/services/mediaService.ts` 1개
- **DB / RLS / Edge Function 변경 여부**: 변경 없음
- **TypeScript 컴파일 및 프로덕션 빌드**: 통과
- **브라우저 검증**:
  - UUID 생성이 정상 동작
  - 이전 실패 과정에서 불필요한 Storage 파일 및 DB 쓰레기 데이터 생성 없음 확인
  - 다음 단계인 Supabase Storage 업로드 통신 단계까지 정상 진입 확인

### 상태
완료

### PPT용 한 줄 요약
> 보안 취약점 없이 Web Crypto fallback을 적용하여 모든 환경에서 안전하게 사진 업로드 단계로 진입하도록 해결함.

## 2026-09-30 — 사진 Storage 업로드 RLS 권한 거부 오류 해결

### 추가한 기능
- Storage RLS 컬럼 섀도잉 방지 마이그레이션 (`20260930100000_fix_media_storage_rls_name_shadowing.sql`)

### 변경한 기능
- Supabase Storage `newsroom-media` 버킷의 접근 제어 정책(INSERT, SELECT, DELETE 3종)에서 파일 경로 참조 명확화

### 발생한 오류
- **오류 메시지**: `파일 스토리지 업로드에 실패했습니다: new row violates row-level security policy`
- **개발자용 설명**: 클라이언트에서 `supabase.storage.from('newsroom-media').upload(...)`를 호출하여 실제 이미지 바이너리를 업로드할 때, 버킷 `newsroom-media`에 적용된 Storage RLS(Row Level Security) 정책 조건을 충족하지 못해 Postgres RLS 정책 위반 에러(`42501`)가 발생함.
- **일반인 설명**: 사진을 서버의 비공개 저장공간에 올리는 단계까지는 정상적으로 도착했으나, 서버가 현재 로그인한 기자의 사진 저장 권한을 허용하지 않아 저장을 거부함.
- **발생 시점 (파이프라인)**:
  - 전체 파이프라인: `[파일 선택] (성공) → [파일 검증] (성공) → [고유 UUID 생성] (성공) → [Storage 업로드 권한 검사] (실패) → [DB 저장] → [Gemini 분석]`
  - 실패 지점: 4단계 Storage 업로드 권한 검사 단계

### 원인
Storage RLS 서브쿼리(`SELECT 1 FROM public.projects p WHERE ...`) 내부에서 컬럼명을 `name`으로만 작성하여, PostgreSQL 파서의 스코프 규칙에 따라 바깥 테이블인 `storage.objects.name`(업로드 파일 경로)이 아니라 안쪽 테이블인 `projects.name`(`p.name`, 프로젝트 제목 문자열)으로 잘못 바인딩(Column Shadowing)됨. 이로 인해 프로젝트 이름에 대해 `storage.foldername`을 파싱하게 되어 항상 `NULL`이 도출되고, `EXISTS` 조건이 무조건 `FALSE`로 판정되어 소유자라 할지라도 모든 Storage 작업이 거부됨 (INSERT, SELECT, DELETE 3종 정책 모두 동일 결함 존재).

#### [초기 조사 과정 및 실패한 시도 보존 기록]
- **초기 확인 상태**: 파일 선택 성공, 파일 형식/크기 검사 성공, 이미지 정보 확인 성공, 안전한 UUID 생성 성공 상태에서 Storage 차단됨.
- **초기 조사 체크리스트**:
  1. 로그인 사용자와 프로젝트 소유자가 일치하는지 여부 점검
  2. 실제 사진 저장 경로 구조(`{projectId}/{uuid}.{ext}`) 일치 여부 점검
  3. 원격 Storage RLS 규칙이 Phase 5 설계와 일치하는지 점검
  4. 실패한 업로드로 남은 고아 파일 및 불완전 DB row 발생 여부 확인
- **해결 원칙 준수**: 보안을 끄거나 모든 사용자에게 public 허용을 주는 임시방편을 절대 배제하고, "프로젝트 소유 기자만 업로드/삭제 가능, 인가된 사용자만 조회 가능" 원칙을 엄격히 고수함.

### 해결 방법
1. 기존 Phase 5 마이그레이션을 보존하고, 신규 마이그레이션 `supabase/migrations/20260930100000_fix_media_storage_rls_name_shadowing.sql` 생성.
2. 서브쿼리 내부의 경로 추출식을 `(storage.foldername(storage.objects.name))[1]`로 명시적으로 한정(qualify)하여 `projects.name` 섀도잉 원천 차단.
3. 3개 정책(`Project owners can upload media objects`, `Users can read project media objects`, `Project owners can delete media objects`) 모두 명시적 경로 참조로 안전하게 교체.
4. `npx supabase db push`로 원격 Supabase DB에 마이그레이션 적용 완료.

### 검증 결과
- **소유자(Owner) INSERT**: PASS (정상 허용)
- **소유자(Owner) SELECT**: PASS (정상 조회)
- **소유자(Owner) DELETE**: PASS (정상 삭제 및 정리)
- **비소유자(Non-owner) INSERT 차단**: PASS (`42501` 정상 거부)
- **비소유자(Non-owner) Private SELECT 차단**: PASS (`0건` 반환으로 완전 격리)
- **비UUID/Malformed 경로 차단**: PASS (`42501` 정상 거부)
- **HR 계정 업로드 차단**: PASS (`42501` 정상 거부)
- **p.name 잘못된 참조**: 0건 확인 완료
- **실제 브라우저 이미지 Storage 업로드**: 성공 확인 및 Gemini Vision API 연동 E2E 파이프라인 진입 성공

### 상태
완료

### PPT용 한 줄 요약
> 사진 업로드 권한 규칙이 파일 경로 대신 프로젝트 이름을 잘못 검사하던 컬럼 섀도잉 문제를 발견하고, 보안 완화 없이 올바른 파일 경로 검사로 정상화함.

### 발생한 오류

- **개발자용 설명**: 사진을 기사 본문에 삽입할 때 클라이언트에서 `article_blocks` 테이블에 INSERT 요청을 보내는 과정에서, DB 테이블 정의에 존재하지 않는 `ai_review_id` 및 `highlighted_text` 필드를 페이로드에 포함하여 PostgREST 스키마 캐시 불일치 오류(`PGRST204`)가 발생함.
- **일반인 설명**: 사진을 기사에 넣을 때 화면 프로그램이 실제 데이터베이스에는 없는 예전 AI 검토용 항목까지 함께 저장하려고 해서 이미지 블록 생성이 거부됨. 데이터베이스를 불필요하게 늘리지 않고, 실제로 존재하는 기사 블록 정보만 저장하도록 수정함.
- **발생 시점 (파이프라인)**: 미디어 라이브러리 → 기사 편집기 이미지 블록 삽입 단계

### 원인
UI 런타임용 상태 필드(`aiReviewId`, `highlightedText`)가 DB 영속화 매퍼에 불필요하게 포함되어 실제 DB 테이블에 없는 컬럼을 INSERT하려 함.

### 해결 방법
1. DB 스키마에 불필요한 임시 컬럼을 추가하지 않음.
2. 프론트엔드 서비스 및 매퍼에서 DB 컬럼과 일치하지 않는 런타임 전용 필드(`ai_review_id`, `highlighted_text`)를 완벽히 제거하여 데이터 정합성 확립.
3. 기사 본문 블록 영속성 데이터와 AI 검토 런타임 상태 간의 명확한 경계 확립.

### 검증 결과
- **수정 파일**: 프론트엔드 기사 서비스 및 매퍼
- **DB / RLS / Edge Function 변경 여부**: 변경 없음 (DB 무결성 보호)
- **TypeScript 컴파일 및 프로덕션 빌드**: 통과
- **실제 브라우저 검증**: 미디어 라이브러리에서 사진 선택 후 기사 편집기에 이미지 블록 삽입 성공, 본문 자동 저장 및 DB 영속화 정상 확인

### 상태
완료

### PPT용 한 줄 요약
> 불필요한 DB 컬럼 추가 없이 화면 데이터 매핑을 정렬하여 기사 내 미디어 블록 삽입 및 저장을 완벽히 복구함.

## 2026-10-02 — 출고 대기 검토(Ready Queue) 미표시 오류 해결 및 공유 상태 분리

### 추가한 기능
- 1:N 프로젝트-기사 관계에서 출고 대기(`ready`) 기사 최우선 상태 파생 로직 (`src/services/mappers.ts`)

### 변경한 기능
- `src/components/dashboard/ProjectDashboard.tsx`: 출고 대기 검토 탭에서 `p.ownerId !== currentUser.id` 필터를 제거하고 `normalizeStatus(p.status) === 'Ready'`를 기준으로 공유 설정(미공개/같은 부서/전체 공유)과 완전히 분리

### 발생한 오류
- **오류 내용**: 기사편집기에서 상태를 `ready`(출고 대기), 공유 상태를 `shared`(전체 공유)로 설정했음에도 부장 계정의 "출고 대기 검토" 탭에 해당 기사가 나타나지 않음.
- **원인**:
  1. `ProjectDashboard.tsx`에서 `reviewQueueProjects` 및 탭 필터링 시 `p.ownerId !== currentUser.id` 조건을 적용하여, 부장 본인이 작성하거나 관여한 기사가 검토 큐에서 원천 배제됨.
  2. 1:N 프로젝트-기사 구조에서 `mapProjectRowToProject`가 단순 첫 번째 기사(`articles[0]`)의 상태만 참조하여, 복수 기사 중 `ready`가 아닌 기사가 먼저 반환될 경우 프로젝트 상태가 `draft`로 파생되어 누락 위험이 존재했음.
- **해결 방법**:
  1. `reviewQueueProjects` 및 `tabFilteredProjects`에서 `p.ownerId !== currentUser.id` 조건을 제거하여, 기사 상태가 `Ready`라면 작성자 본인 여부 및 공유 설정(`private`/`shared` 등)과 무관하게 모두 출고 대기 검토 대상이 되도록 정렬.
  2. `mappers.ts`에서 프로젝트 내 `articles` 중 `ready` 상태인 기사가 존재할 경우 최우선으로 대표 기사로 선택하여 파생 상태가 `Ready`가 되도록 보강.
  3. 공유 설정(`visibility`)은 일반 사용자 프로젝트 열람 범위에만 관여하고, 출고 대기 검토 파이프라인과는 완전히 독립 분리함.

### 검증 결과
- **CASE 1 (기자 작성 + 미공개 private + ready)**: PASS (출고 대기 검토 목록에 정상 표시)
- **CASE 2 (기자 작성 + 같은 부서 공유 + ready)**: PASS (출고 대기 검토 목록에 정상 표시)
- **CASE 3 (기자/부장 작성 + 전체 공유 shared + ready)**: PASS (부장 본인 작성 기사 포함 출고 대기 검토에 정상 표시)
- **CASE 4 (draft 기사)**: PASS (출고 대기 검토 목록에서 제외 확인)
- **CASE 5 (1:N 복합 기사 draft + ready)**: PASS (`ready` 기사 우선 선택되어 정상 표시)
- **기존 데이터 수정 여부**: 수정 없음 (0건)
- **TypeScript 린트 및 프로덕션 빌드**: PASS (`tsc --noEmit`, `vite build` 통과)

### 상태
완료

> 작성자 필터 결함을 제거하고 공유 설정과 출고 대기 검토를 분리하여, 기사 상태가 ready이면 어떤 공유 설정이든 부장 검토 큐에 즉시 노출되도록 개선함.
